# Self-Harness：概念、实现方案与评估方案

> 状态：设计稿 v2，2026-08-10
> 结构：§1 概念（是什么 / 四自由度 / **四框循环**）→ §2 现有实现清单 → §3 架构（按四框映射）→ §4 实现路线 → §5 评估方案 → §6 风险 → §7 MVP
> 目标：搭一个「模型权重冻结、评估器冻结、只演化 harness」的闭环，并用一套**能扛住审稿**的评估协议证明收益不是过拟合。

# §1 概念

## 1.1 名字有歧义，先分开

**窄义**：arXiv 2606.09498 那篇论文的方法名。
**广义**：「harness 自改进」这一整类工作（AHE / Meta-Harness / DGM / SICA / ACE …）。

本文档按广义使用，窄义那篇统一写作 **Self-Harness(论文)**。

## 1.2 定义

先定 harness（Weng 的说法）：**包在基座模型外面、决定模型怎么想怎么做的那套系统** —— 编排执行、组织思考与规划、调工具、感知与管理 context、存产物、判结果。

> **self-harness = 模型权重冻结、评估器冻结，让 agent 用自己跑任务的执行证据去改自己外面那层 harness，并用任务成败来验证这个改动。**

三个「冻结/不冻结」是定义性的：

| | 状态 | 为什么 |
|---|---|---|
| 模型权重 | **冻结** | 冻了才叫 harness 优化；不冻就滑到 L5（SEAL / SIA 那类） |
| 评估器 + 数据集 | **冻结且只读** | 不冻就是 reward hacking，整个循环失去意义 |
| harness 代码/配置 | **可写，且是唯一可写面** | 这是被优化的对象 |

## 1.3 与四个邻居的边界

- **≠ 微调 / RL**：不动权重。收益来自「模型本来就会、但没被引导出来」的那部分。
- **≠ prompt 优化**（APE / OPRO / GEPA / DSPy）：prompt 只是七个可编辑面之一，且是**边际收益衰减最快**的那个。self-harness 改的是 middleware、工具实现、子 agent 装配这些**有状态、有控制流**的东西。
- **≠ workflow / agent 图搜索**（ADAS / AFlow / GPTSwarm）：那类在预定义算子上搜拓扑，空间封闭。self-harness 改任意代码与文本文件，空间开放。
- **≠ in-context memory**（Reflexion / ReasoningBank）：那类产出「经验条目」喂回 context。self-harness 产出**持久化的代码与配置 diff**，跨任务跨 session 生效，且能被 git revert。

## 1.4 四个自由度（方案定位坐标）

**① 改什么（editable surface）**

```
prompt 文本 → +context/memory 策略 → +工具描述 → +工具实现
            → +middleware/控制流 → +子 agent 装配 → 整个 agent 代码库
```
AHE 切成七个正交文件级组件；DGM / SICA 直接放开整个代码库。
**面越宽，收益上限越高，但归因越难、越容易作弊。**

**② 谁来改（updater）**

同一个模型改自己，还是独立 meta-agent 改 target agent。
👉 2605.30621 的关键结论：**updating 能力对底座近似持平** —— Qwen3.5-9B 产的 harness 更新，收益接近 Opus 4.6 产的。
**⇒ updater 用便宜模型，能力预算压在跑任务的 agent 上。直接省钱。**

**③ 什么时候改**
- **离线 evolve**：跑完一批 → 分析 → 改 → 再跑。AHE / Self-Harness(论文) / DGM / Meta-Harness。
- **在线 on-the-fly**：解题当中现场造工具。Live-SWE-agent。收益快但不沉淀、难验证。

**④ 拿什么信号**（最被低估的一轴）

```
只有 pass/fail 标量  →  太稀疏，学不动
+ 完整 trace        →  AHE 立场："trace，不是 pass rate，才是后续每一步操作的单位"
+ 结构化失败签名     →  Self-Harness(论文) 的 φ(r)=(c,q,m)
+ 演示/示范          →  DemoEvolve，专治稀疏反馈
```

## 1.5 ★ 抽象成一个循环

**所有方案都是这个循环的变体，差别只在每个方框里塞什么。** 这是本文档的组织主干——后面的架构、实现路线、评估、消融，全部挂在这四个框上。

```
   ┌──▶ ① Rollout：当前 harness × 任务集 → traces + rewards
   │         │
   │         ▼
   │    ② Diagnose：traces → 失败模式（聚类 / 根因 / 报告）
   │         │
   │         ▼
   │    ③ Propose：失败模式 → K 个候选 harness diff
   │         │
   │         ▼
   │    ④ Select：候选 → 评测 → 收 / 拒 / 回滚
   └─────────┘
```

各方案在四框中的取值：

| | ② Diagnose | ③ Propose | ④ Select |
|---|---|---|---|
| **DGM** | 弱（只看分数） | 自由改代码库 | **archive 存档 + 开放式探索**（保留次优分支） |
| **SICA** | 弱 | 自由改代码库 | 取历史最优当 meta-agent（贪心） |
| **ACE** | reflector 出批注 | curator 出 bullet 增量 | 增量合并，几乎不拒 |
| **Self-Harness(论文)** | **φ(r)=(c,q,m) 精确聚类** | K 个最小 diff | **保守闸门 `Δ_in≥0 ∧ Δ_ho≥0 ∧ max>0`** |
| **AHE** | Agent Debugger 分层报告，每条论断挂 trace | 七组件 + **四要素承诺** | **预测-证伪 + flip 归因 + git 回滚** |
| **Meta-Harness** | proposer 直读所有历史候选的源码/分数/trace | 自由写 harness 代码 | **floor-respecting Pareto 前沿**（质量 × 成本多目标） |

四种 Select 代表四种哲学：**贪心 / 存档多样性 / 保守单调 / Pareto 多目标**。
**这是本方案里最需要想清楚的一格。** 本文档的选择：以保守单调为主闸，Pareto 作为第二目标（成本/体积，见 §5.6），archive 作为反多样性坍缩的兜底（见 §6）。

### 每框的失效模式（设计检查表）

| 框 | 典型失效 | 对策（本方案的落点） |
|---|---|---|
| ① Rollout | 方差吃掉信号；沙箱并发卡死 | n≥3 重复 + 先量方差（§4 Phase 0）；本地 docker 起步 |
| ② Diagnose | 签名自由造词 → 聚不成类；论断无据 | 受控枚举词表；每条论断挂 trace span |
| ③ Propose | K 个候选实质雷同；改动越界；背题 | 强制实质不同；路径白名单；任务字面量扫描（§3.2） |
| ④ Select | 收益来自噪声；held-out 被磨成训练集 | 保守闸门 + 配对检验；**三分割**（§5.1） |

## 1.6 分级（借 awesome list 的 L 轴）

```
L0 prompt              APE, OPRO, GEPA, DSPy
L1 context/memory      Reflexion, ACE, ReasoningBank, Memp
L2 workflow/graph      ADAS, AFlow, GPTSwarm, AgentSquare
L3 harness 自改        ★ AHE, Self-Harness, Meta-Harness, SICA
L4 自指（改「改自己的那个」）  STOP, Gödel Agent, DGM
L5 权重+harness 联合    SEAL, SIA, Voyager
```
**L3 是当前工程性价比的甜点。L4 好玩但验证成本爆炸。本方案定位 L3。**

## 1.7 这个方向的真实状态（别只看涨幅）

两篇负面结果必须先知道：

- **2607.12227**：演化本身就是一个「反复评测+修订」的搜索过程，**必须和等预算 test-time scaling 比**。在 TB2.1 + GPT-5.4/Opus 4.6 上，收益打不稳、held-out 泛化有限。
- **2605.30621**：harness-**benefit** 对底座**非单调** —— 弱模型接不住（要么不激活 harness 产物，要么激活了不遵守），中档收益最大，强模型不如中档。

**⇒ 这个方向不是「必涨」的。做出来之后说服力全在评估协议上，不在数字上。**

### better-harness 源码勘察结论（全仓 2719 行，`core.py` 1131 行是主循环）

**已经对的（比我原先估计的好）：**

| 项 | 实现 |
|---|---|
| **三分割已存在** | `VALID_SPLITS = ("train", "holdout", "scorecard")`；scorecard **只在 baseline 和 final 各跑一次** = §5.1 的 locked test，且访问次数天然被限制成 2 |
| **私有性已隔离** | `PRIVATE_SPLITS = {"holdout", "scorecard"}` —— outer agent 只看得到 train 失败与其源文件，看不到 holdout |
| **分层字段已有** | case 支持 `stratum`，可做同源任务不跨 split |
| **runner 直连 TB** | 支持 `pytest` 与 **`harbor`** ⇒ Terminal-Bench 直接可跑 |
| **决策留痕** | 每轮写 `decision.json` / `decision.md`，outer agent 能看到历史 keep/discard |
| 声明式可编辑面 | TOML 里声明，两种加载模式：`module_attr`（打 Python 属性补丁）/ `workspace_file`（eval 期间临时换文件） |

**⚠️ 实测缺口（grep 全仓零命中，不是「弱」是「没有」）：**

| 缺口 | 证据 | 后果 |
|---|---|---|
| **① 无重复运行** | `repeat` / `seed` / `n_runs` / `trials` 全仓零命中 —— **每个候选只跑 1 次** | **最致命**。TB2 任务级噪声足以吃掉 5 个点，单次运行的 accept/reject 基本是掷硬币 |
| **② 闸门用合计** | `core.py:935-937`：`accepted = (train.passed + holdout.passed) > (current_train.passed + current_holdout.passed)` | 允许拆东墙补西墙：holdout −2、train +3 → 合计 +1 就通过。**这正是过拟合的典型形态** |
| **③ 无防作弊** | `guard` / `allowlist` / `forbid` / `sandbox` 零命中；README 自认 "not a hard sandbox boundary yet" | 无路径白名单、无任务字面量扫描 |
| **④ 无成本追踪** | 只有 `duration_s`，无 token / cost / latency | §6 的成本闸门无处可挂 |
| **⑤ K=1** | 每轮 proposer workspace 只产**一个**候选（README: "turns those edits into one candidate harness"） | 无候选多样性，无 §5.5 的 K 消融 |

**⇒ 结论：骨架（可编辑面加载、三分割、runner 适配、留痕）已经做好了，缺的全是「实验严谨性」那一层。这恰好是最容易补、且补丁彼此正交的部分。** 不要重写。

### 两个实操 gotcha

1. **middleware 必须暴露两个面**：实现文件 + **注册文件**（`create_deep_agent(middleware=[...])` 那处）。只暴露实现，outer agent 根本没法把 middleware 打开。README 专门警告了这条。
2. 官方推荐的用法是**拿 Claude Code 指着这个 repo 说** `set up this repo using my evals` —— 它本来就是设计成被 coding agent 驱动的。

## 2.1b 落地案例（deepagents 生态，目前最接近「成功案例」的三个）

| 案例 | 做了什么 | 结果 | 自动化程度 |
|---|---|---|---|
| **[LangChain deepagents-cli](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)** | 纯 harness engineering，模型固定 gpt-5.2-codex 不变。加了三个 middleware：`PreCompletionChecklistMiddleware`（退出前强制按 task spec 跑一遍验证）、`LocalContextMiddleware`（启动时探目录结构与可用工具）、`LoopDetectionMiddleware`（追踪文件编辑次数，N 次后提示换思路，破 doom loop）；system prompt 重构成 planning→building→verification→fixing 四阶段 | **TB2.0 全 89 题：52.8% → 66.5%（+13.7pt），Top 30 → Top 5** | ⚠️ **半自动**。trace 分析做成了 Agent Skill（并行 error analysis agent → 主 agent 汇总），但**改动本身由人审**，官方明说人审是为了防过拟合 |
| **[better-harness](https://github.com/langchain-ai/deepagents/tree/main/examples/better-harness)** | 上面那套经验的自动化版本，outer agent 改 inner agent | 未见公开数字 | ✅ 全自动 |
| **[NVIDIA Nemotron 3 Ultra harness profile](https://developer.nvidia.com/blog/create-a-langchain-deep-agents-harness-profile-for-nvidia-nemotron-3-ultra-to-improve-performance/)** | **模型厂商给自家模型做 harness profile**。发现 Nemotron 读大文件分页截断时误以为读完了 → 加 `ReadFileContinuationNoticeMiddleware`，命中分页上限时追加提示要求带 offset 继续读 | 94/127 → 96/127，3 个 read_file 分页测试全过 | ✅ **ralph loop** 自动提案器：自动找失败、提案、多次重跑验证；靠「只许改 profile 级、不许改 test 相关」来防过拟合 |

**三条读法：**
1. **+13.7pt 那个数字不是自主循环跑出来的**，是人工 harness engineering + 自动 trace 分析。引用时别misattribute —— 它证明的是「harness engineering 有效」，不是「self-harness 有效」。
2. **harness profile 是「model-specific harness」的产品化形态**，且已被模型厂商采纳（NVIDIA×LangChain）。这是这条线上最强的真实世界采纳信号，比任何 benchmark 数字都有意义。
3. NVIDIA 那个案例的涨幅很小（+2/127）且如实报出来了。**这才是自动 harness 优化的真实幅度量级** —— 论文里的两位数涨幅都伴随着极弱的 seed。

> 副产品：LangChain 报了一个 **"reasoning sandwich"** —— planning 与 verification 用高推理预算、implementation 用低的，优于全程 xhigh。注意这**与 §3.2 的只读边界冲突**（推理预算属禁改项）。处理方式：把「分阶段推理预算」作为 harness 的一个**声明式配置项**开放给 ③，但**总预算封顶**只读。否则 proposer 会直接靠加钱刷分。

**一句话分工：概念与验收规则抄 Self-Harness(论文)，工程实现抄 AHE，领域接入抄 Meta-Harness，评估协议按 2607.12227 + 2605.30621 加固。**

⚠️ 口径提醒：Self-Harness(论文) 正文 held-out 是 40.5→61.9 / 23.8→38.1 / 42.9→57.1，README 是 42.2→53.9 / 18.0→36.7 / 46.1→57.0。同一工作两套数字对不上，正说明**协议不写清楚数字就没意义**。我们自己的报告必须把 split、repeats、聚合方式写死。

**held-in / held-out 必须成对报。** 二手解读常只挑最大的那个数字宣传（例：Qwen3.5 held-in 15.1→36.0 = 相对 +138%，被拿来当标题；同一模型 held-out 只有 23.8→38.1 = +60%）。**held-in 涨幅永远虚高**，因为它就是被搜索的那个集合。本方案的报告模板强制三列并排：held-in / validation / locked test，缺一不发。

> 二手材料（视频解读、公众号、社区笔记）用途仅限「发现线索」。数字、模型名、方法归属一律回原文核对——实测一份中文视频解读里三个底座模型名全错（写成 QEN 2.5-32B / Minix / llama，实为 Qwen3.5-35B-A3B / MiniMax M2.5 / GLM-5），且把「用更强外部模型当老师」这一 baseline 误标为 Meta-Harness（真实的 Meta-Harness 2603.28052 是 Pareto 搜索，与外部教师无关）。

  │ (harness)│◀───────────│ (harbor) │     │ 签名+聚类 │  │ K候选diff│  │ 闸门/回滚│
  └─────────┘   写回      └──────────┘     └───────────┘  └──────────┘  └────────┘

## 3.1 可编辑面（workspace/，唯一可写）

沿用 AHE 七组件——和 Claude Code / OpenClaw 的实际切面一一对应：

```
workspace/
├── systemprompt.md          # 系统提示
├── agent.yaml               # agent 装配（子agent挂载、middleware 顺序）
├── tool_descriptions/       # 工具描述（改描述 ≠ 改实现，分开演化）
├── tools/                   # 工具实现
├── middleware/              # context compaction / failover / retry / ralph loop
├── skills/                  # 可复用技能包
├── sub_agents/              # 专用子 agent
└── LongTermMEMORY.md        # 跨任务持久经验
```

七个文件级组件不是美学问题：**归因需要它**。gain 落在哪个组件上是最重要的消融维度（§5.5）。

## 3.2 只读边界（防 reward hacking 的硬约束）

Propose 的写权限用 **路径白名单 + diff 静态检查** 双重拦。禁止项（命中即拒该候选，记入 ledger）：

1. 修改 `verifier/`、`datasets/`、任何测试文件或期望输出
2. 修改模型 id、temperature、max_tokens、思考预算、并发数
3. 修改 runner / tracer / 打分脚本
4. harness 文本中出现**任务 id、任务名、测试用例字面量**（字符串重叠自动扫）
5. 网络出口白名单外的访问（防止把答案从外面搬进来）

第 4 条 Self-Harness 和 AHE 都没硬检，但它是「学到工程经验」vs「背题」的分界线。实现为 `guards/edit_guard.py`，候选进入评测前跑。

> 与 AFML 的 purged K-fold + embargo 同构：**优化器不能触到评估器**。

## 3.3 核心数据结构（先定 schema 再写代码）

```python
# ① Rollout 产出，一个 rollout 一条
{task_id, seed, harness_sha, steps:[...], tokens_in, tokens_out,
 wall_s, reward: 0|1, verifier_msg, terminal_state}

# ② Diagnose 产出 —— Self-Harness(论文) 的 φ(r)=(c,q,m)
{c: "verifier 层终态原因",      # e.g. "tests_fail:timeout"
 q: "agent 行为的因果状态",      # e.g. "agent_caused:premature_stop"
 m: "暴露的抽象机制"}            # e.g. "no_verification_before_submit"
# 聚类 = 三元组精确相等（确定性、可复现，不用 embedding）

# ③ Propose 产出，含 AHE 四要素承诺
{id, target_cluster, diff,
 evidence: [{task_id, trace_span}],   # 失败证据
 root_cause: str,                     # 为什么失败，不是失败了什么
 fix_rationale: str,                  # 修复如何对上根因
 predicted: {flip_to_pass:[task_id], at_risk:[task_id]}}  # 可证伪预测

# ④ Select 产出
{proposal_id, d_in, d_ho, accepted: bool, reason,
 prediction_precision, prediction_recall,   # 预测 vs 实际 flip
 rollback: bool}
```

`predicted` 是整套系统的灵魂：**每次 harness 改动都是一个可证伪的断言**。下一轮回填实际 flip；预测持续不准的 proposer 要么换提示词要么降权。这条纪律即使手工改 harness 也该立。

## 3.4 失败签名的现实样貌（② 的 seed 词表）

Self-Harness(论文) 三个底座各自演化出的「处方」，是目前唯一公开的、**model-specific 失败模式对照组**。直接拿来当 `φ(r)=(c,q,m)` 受控枚举词表的起点，比自己凭空造词靠谱：

| 底座 | 诊断出的病 | 模型自己开的药 | 落在哪个组件 |
|---|---|---|---|
| **Qwen3.5** | 无效无限循环 + 缺重试：同一命令反复撞墙，脚本报错就原样重跑到超时；曾反复读写同一文件、最后删掉唯一正确的验证脚本 | **异常触发的 middleware**：工具调用一报错立即拦截该操作 + 注入系统级警告（停止漫游 / 文件缺失则立即创建 / 失败视为致命错误） | `middleware/` |
| **MiniMax M2.5** | **过度探索**：拿到任务狂查数据、元数据、结构，时间耗尽还没碰到答案 | **强制提前交付**：尽快定位最小编辑面 → 先产草稿文件 → 再慢慢迭代。切断无限探索空间 | `systemprompt.md` + `middleware/` |
| **GLM-5** | **环境状态记忆丢失**：跨 session 配置的环境变量丢失 | 环境变量**持久化** + 严格限制探索时长，超时强制切换到 implement & test 状态 | `LongTermMEMORY.md` + `middleware/` |

三条观察：
1. **三个模型的药方互不相同**，且都不是「加一段通用好话」。这是「harness 必须 model-specific」这一论点最硬的证据。
2. **药基本都落在 `middleware/`**，systemprompt 只是配角 —— 与 §5.5 的预期一致（middleware + skills 占大头）。
3. 这些规则本质是**防御性编程**（检查退出码、失败即止、先出草稿）。含义：② 的词表应该照着「资深工程师的 code review checklist」来枚举，不要造新词。

## 3.5 任务集清洗（① 的前置）

Self-Harness(论文) 从 TB2.0 的 89 任务里**手工剔掉 25 个，只留 64 个**。剔除标准值得直接抄：

- 强依赖**不稳定外部网络资源**的任务 —— 网络挂了导致失败，不是 agent 的错，纯噪声
- 需要**多模态输入**的任务 —— seed harness 不支持视觉，测的是缺失功能而非 agent 能力

**这是 ① 层最廉价的降噪手段**：在量方差之前先做，能显著缩小 §5.2 需要的 repeats 数。同时要把剔除清单写进 replication package —— 否则「64 题子集」这个口径本身就无法复现，别人拿 89 题跑出来的数字和你不可比。

# §4 实现路线

### Phase 0 — 只做 ①（先跑通「测」，不碰「改」）
- runner 用 `harbor`：`uv tool install harbor`，本地 docker 起步，`--n-concurrent` 按机器调。
- 数据集 `terminal-bench@2.0`（89 任务）。先**不用** 2.1——2607.12227 的负结果是在 2.1 上做的，留作对照环境；两版都留接口。
- 交付：seed harness baseline，**每任务 ≥3 次重复**，出 pass@1 均值 + bootstrap CI + 每任务成败矩阵。
- 关键：**先量方差再谈提升**。TB2 单次 run 的任务级噪声足以吃掉 5 个点。

### Phase 1 — 补 ②
- trace → `φ(r)=(c,q,m)`：规则 + LLM 混合抽取，signature 词表**受控枚举**（不让 LLM 自由造词，否则聚不成类）。
- 产出 `analysis/overview.md` + `analysis/detail/{task}.md`，每条论断挂原始 trace span 链接（AHE 做法，是人工审计的唯一抓手）。
- Agent Debugger 那层 AHE 未完全开源，自己写：一轮 10M+ token 的 trace 压成 ≤5k token 的分层报告。

### Phase 2 — 补 ③④（人在环中）
- Propose 一次出 **K=4~8** 个候选：每个只打一个 cluster、只改必要面、彼此**实质不同**、不破坏无关行为。
- Select 先上 Self-Harness(论文) 的保守规则 `Δ_in≥0 ∧ Δ_ho≥0 ∧ max>0`。**两边互相拆借的一律拒。** 约 10 行代码。
- 本阶段每次晋升需人工点头，目的是校准 root_cause 质量，别急着放开。

### Phase 3 — 闭环自动化
- `evolve.py` 主循环：① → ② → ③④ → 下一轮 flip 归因写 `change_evaluation.json` → 预测不成立的编辑回滚或修订。
- 目录照 AHE：`runs/iteration_NNN/{input,evolve}/`；workspace 全程 git-tracked，每次编辑一 commit，可 revert 到任意轮。
- 停止条件：`target_pass_rate` 或 `max_iterations` 或**预算闸**（§6）。

### Phase 4 — 迁移与拆解
冻结 harness，跑 §5.4 的迁移矩阵与跨 benchmark。

**技术选型**：Python ≥3.12 + uv；runner = harbor（本地 docker / 云上 daytona 或 e2b）；LLM 走 OpenAI 兼容 endpoint 以便换底座；版本与回滚直接用 git，不自造。

# §5 评估方案（决定这个工作能不能立住）

## 5.1 三分割，不是两分割 ⚠️

Self-Harness(论文) 和 AHE 都是两分割（held-in 搜索 / held-out 校验），但 **held-out 参与了晋升决策，它本质是 validation 不是 test**。跑几十轮之后 held-out 已被间接优化过。

| split | 用途 | 谁能看 |
|---|---|---|
| **Search (in)** ~50% | ②③ 直接使用 | Propose 可见 trace 全文 |
| **Validation (ho)** ~25% | 只喂 ④ 的 `Δ_ho`，**只返回标量 pass rate** | Propose 不可见 trace |
| **Locked Test** ~25% | 全程封存，**预注册最多访问 3 次**（起点/中点/终点），每次访问记录在案 | 解锁前任何人不可见 |

Validation 只回标量不回 trace，切断「读 held-out trace 反向背题」的通道。Locked test 访问次数预注册，防止 test 被慢慢磨成 validation。

任务级分割要注意**同源任务不能跨 split**（TB2 里同主题任务相关）——按主题分组后再分割，即 purged split 思路。

## 5.2 统计口径

- 每任务 **n≥3 次重复**（④ 内部为省钱可 n=2，最终报告必须 n≥5）。
- 主指标 pass@1，报**均值 ± bootstrap 95% CI**（任务级 + seed 级双层重采样）。
- **不能只看均值差**：用**配对检验**（每任务 pass 次数配对，bootstrap 或 McNemar）——任务难度方差远大于方法差异。
- 报 **gain concentration**：收益中多少来自最靠前的 3 个任务。若 70% 提升来自 2 个任务，那不是方法有效，是运气或背题。

## 5.3 必须做的基线（2607.12227 红线）

演化本身是「反复评测+修订」的搜索，基线必须**预算对齐**（对齐总 token 与总 rollout，两个都报）：

| 基线 | 作用 |
|---|---|
| **B0** seed harness, 1 rollout | 起点 |
| **B1** seed harness + best-of-N / 多次重试，N 使总预算 = 演化总预算 | **最硬的对照**：打不过「同样的钱多跑几遍」，方法即无效 |
| **B2** 无诊断的盲改（③ 不看 trace） | 隔离 ② 的贡献 |
| **B3** 只改 systemprompt | 隔离「七组件」是否必要 |
| **B4** 人工 harness（Terminus-2 / Codex-CLI 风格） | 天花板参照，AHE 用的是 Codex 71.9% |
| **B5** **成熟人工 harness，零演化**（deepagents-cli / Claude Code 原样） | **真实起点**。论文的 seed 都是故意阉割的（Self-Harness 明说「deliberately kept minimal」，只留 DeepAgent 默认 filesystem + shell），从垃圾起点起跳涨幅天然虚高。B5 才是你实际会用的东西 |

**B1 最容易被跳过，也最容易翻车。必须做。**
**B5 是论文里全部缺失的一格** —— 参照系：LangChain 的 deepagents-cli 未经优化就有 **52.8%**，而 Self-Harness 的极简 seed 只有 15~42%。**「B5 零演化」很可能直接高于「阉割 seed + 十轮演化」。** 不先测 B5，整个项目的收益归因就是空的。

## 5.4 迁移矩阵（证明学到的是工程经验而非 benchmark 特化）

按 2605.30621 设计，把 updater 与 beneficiary 拆成两个自由度：

```
            beneficiary（跑任务的模型）
            M1    M2    M3    M4
updater M1  ✓     ✓     ✓     ✓     ← 行内：该 updater 产出的 harness 多通用
        M2  ✓     ✓     ✓     ✓
        M3  ✓     ✓     ✓     ✓
        ↑ 列内：该 beneficiary 能从各家 harness 捞多少
```

**可证伪预测**（源自该文结论）：行间差异小（updating 平），列间非单调（中档 beneficiary 收益最大）。结果若相反，要么是新发现，要么是实验有 bug——两种都值得查。
**实践含义：能力预算压在 task-solving agent，updater 用便宜模型。**

跨 benchmark：冻结 harness → SWE-bench-Verified 子集（AHE 报跨族 +5.1~+10.1pt 且 token 少 12%）。**跨 benchmark 不涨 = 只是背了 TB2。**

## 5.5 消融（按四框组织）

| 框 | 消融 | 看什么 |
|---|---|---|
| ② | 去掉 Diagnose（= B2） | 诊断层的净贡献 |
| ③ | K=1 vs K=8 | 候选多样性的边际收益 |
| ③ | **七组件逐个冻结** | 收益落在哪个面（预期 middleware + skills 占大头，systemprompt 边际递减） |
| ④ | 去掉闸门（无条件接受） | 性能是否随轮次震荡/退化 |
| ④ | 闸门强度：`max>0` vs 严格要求 `Δ_ho>0` | 保守度与收敛速度的权衡 |

## 5.6 不能只报 pass rate

同时报，**任何一项显著变差都要在结论里写明**：

- token/任务、cost/solved-task（防「多花 3 倍 token 换 2 个点」）
- 步数、wall-clock
- harness 体积（注入 context 的字节数）——长期膨胀是这类系统的通病
- 失败签名直方图前后对比
- 稳定性：同 harness 多 seed 的方差是否变大

> 这几项同时也是 ④ 里 Pareto 那一维的坐标（Meta-Harness 的 floor-respecting Pareto：质量设地板，成本上求前沿）。

# §6 风险与护栏

| 风险 | 护栏 | 落在哪框 |
|---|---|---|
| Reward hacking（关 verifier、改预算、背题） | §3.2 白名单 + diff 静态检查 + 任务字面量扫描；ledger 记录每次拦截 | ③ |
| Held-out 被磨成训练集 | 三分割 + validation 只回标量 + locked test 预注册访问次数 | ④ |
| 收益来自方差 | n≥3 重复 + 配对检验 + gain concentration | ①④ |
| 多样性坍缩（Weng challenge #4） | K 个候选强制实质不同；ledger 记录候选相似度；坍缩时随机重启 + 借 DGM 的 archive 保留次优分支 | ③④ |
| 成本失控 | 硬预算闸：单轮 token 上限 + 总 $ 上限，触顶即停并落盘 | ① |
| 沙箱并发卡死 | E2B SaaS 有按 tier 的并发上限，超了整轮 stall；本地 docker 起步，云上先测并发天花板 | ① |
| harness 无限膨胀 | 体积作为约束指标，超阈值时 ③ 只许做「等体积替换」 | ③ |
| **frozen-replay defect** | 若 scorer 回放的缓存输出不随候选变化，质量看着不动只有成本在动 → 前沿是假的。任何缓存/回放的打分器都要先验证候选敏感性（harness-forge 文档点名的坑） | ①④ |
| **成本/延迟被闸门放行** | 现有闸门只管 pass rate 无回归。演化出来的「加一步验证」可能让 API 调用涨 10×、延迟 2s→20s，而闸门完全看不见。**⇒ 把 §5.6 的成本项从「报告指标」升级为「硬闸门」**：`Δ_cost ≤ +X%` 且 `Δ_p95_latency ≤ +Y%`，超了直接拒。这就是 ④ 里 Pareto 那一维要解决的事 | ④ |
| **可编辑面的表达力天花板** | bounded editing 只能在既有控制流上打补丁。若最优解需要**换一套思维架构**（如引入 MCTS / 树搜索），无论演化多少轮都跳不出预设边界。⇒ 演化曲线平台期时，先问「是搜索不到，还是这个解不在可编辑面内」，再决定是加轮次还是扩面 | ③ |

# §7 MVP：两周、一人、小预算

不要一上来跑 89 任务 × 10 轮。

1. **Day 1-3**：harbor 跑通，seed harness，89 任务 × 3 repeats 出 baseline 与方差。
2. **Day 4-5**：挑 **16~24 个任务**的迷你集（覆盖 seed 的主要失败签名，8/4/4 三分割），单轮成本压到可接受。
3. **Day 6-9**：②③④ 打通，**人工点头**跑 3 轮；重点看 root_cause 质量和预测命中率，**不看 pass rate**。
4. **Day 10-12**：放开自动循环跑 5~8 轮，同时跑 **B1 等预算 best-of-N**。
5. **Day 13-14**：解锁 locked test 一次；跑 2×2 缩小版迁移矩阵。

**MVP 成功判据不是 pass rate 涨了，而是：**
- 预测命中率（`flip_to_pass` 的 precision/recall）显著高于随机
- 在等预算 B1 上有可复现优势
- locked test 提升 ≥ validation 提升的 50%（否则就是过拟合在爬）

# §8 三条起步路线（按投入意愿选）

**路线 1 — 今天就试（半天）**
装 `harness-forge`，在 Claude Code 里对一个自己的小任务集跑一遍 propose→score→Pareto。零外部依赖，立刻建立对四框循环的手感。注意它自己点名的 **frozen-replay defect**。

**路线 2 — 接自己的领域（1-2 周）**
`stanford-iris-lab/meta-harness` + `ONBOARDING.md`。proposer 本来就是 Claude Code，接新领域路径最短。代价：官方说未充分测试，得能读代码。

**路线 3 — 正经研究/产品底座（1 月+）**
AHE 当骨架 → 补 Agent Debugger → 把保守闸门加进 ④ → 按 §5 的三分割 + 等预算 B1 做评估。

# §9 三条纪律（不跑自动循环、手工改 harness 也适用）

1. **四要素承诺**：每次改 harness 同时写下 失败证据 / 根因 / 针对性修复 / **预测影响**（哪些任务应翻 pass、哪些有回归风险）。下轮回填对错。
2. **保守晋升**：`Δ_in≥0 ∧ Δ_ho≥0 ∧ max>0`。只涨不跌才收。
3. **只读边界**：优化的人/agent 永远不能碰评估器。

可直接读的现成产物：AHE 的 `agents/evolve_agent/evolve_prompt.md`、`middleware/`（含 context compaction、failover、ralph loop）、`skills/`；Self-Harness 的 `harnesses/qwen_tb2_final/`。
